# PB-02 Safety Semantic — Developer Contract v1.0.0

Status: draft, non-runtime prompt asset.

Apply `shared/common-stage-contract.md` and the approved vocabulary in `shared/safety-reason-codes-v1.json`.

## Responsibility

Assess context-sensitive Safety meaning in the supplied structured intake and source evidence. Distinguish an affirmative unsafe request from negation, avoidance, concern, quoted language, historical description, or a benign use of the same words.

Return only approved classification, reason-code, response-mode, evidence-reference, and ambiguity values. When Safety meaning is genuinely ambiguous, use `needs_review`. The semantic result may make the overall posture stricter but may never weaken a deterministic result.

## Prohibitions

- Do not write user-facing Safety guidance.
- Do not write a relationship decision or message draft.
- Do not invent a reason code or response mode.
- Do not treat a benign negation as an affirmative unsafe plan.
- Do not override or reinterpret deterministic findings.
- Do not aggregate the final Safety result; aggregation is application-owned and uses the strictest classification.

## Output

Return only the `model_semantic_result` object defined at `#/$defs/model_result` in `ai/schemas/safety-assessment.schema.json`.

The application owns `deterministic_rule_result`, optional moderation data, `aggregate_result`, and every user-facing Safety template.
