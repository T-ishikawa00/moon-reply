## 0. 使い方

このガイドは、Humanが運営上の判断を行うための説明資料である。推奨案はプロジェクト上の初期方向であり、Humanの最終判断、provider-specific authoritative approval/review evidenceまたは最新の公式一次情報と実際のProduct/運用証拠の確認を代替しない。Stripeはdesired strategic primary Candidateにすぎず、feasibility、approvalまたはformal selectionではない。PAY.JPはpaused fallbackである。

回答は `OPERATOR_DECISION_WORKSHEET.md` に記録し、根拠となる契約、最新の公式一次情報、設定画面および試験結果を紐づける。専門家相談を利用する場合は任意の補助証拠として記録できるが、Paid LaunchまたはProduction Paymentの必須条件ではない。

Current sequencing: Stripe strategy CandidateのHuman + ChatGPT integrated reviewが次作業である。Legal identity、住所・電話表示、final support email、Tokushoho publication、opening notificationおよびvirtual officeは解決しておらず、将来のapplicable Provider review/publication/Paid Launch前に実証が必要である。ただし、GMO契約、開業届その他のPAY.JP固有準備はpaused fallbackであり、現行Stripe Candidate reviewのblockerまたはcurrent requirementではない。住所・電話表示方法は、最新の公式一次情報とactual selected Provider evidenceを得た将来判断で確定する。

## OP-001 運営形態

- **何を決めるのか:** 月の返事を個人、個人事業主、法人のどの主体で運営・契約・表示するか。
- **なぜ必要なのか:** 決済事業者との契約主体、特商法表記、税務・会計、問い合わせ対応主体を一致させるため。
- **選択肢:** 個人 / 個人事業主 / 法人。
- **推奨案:** 有料公開前の未確認状態を禁止する。運営形態はprovider契約と法務表示の主体に一致させる。法務・税務上の判断は必要に応じて専門家に確認する。特定の形態が常に最適とは結論しない。
- **今すぐ決める必要があるか:** 現行Stripe Candidate reviewでは決めない。将来のapplicable Provider契約・審査および公開用法務文書へ実情報を入れる前に必要。現在は未決定のまま。
- **証拠・確認先:** providerの申込資格・契約条件、最新の税務・法務公式情報、実際の事業届出・法人情報。PAY.JPの個人/個人事業主routeでは開業届またはcurrent guidanceが認めるequivalent document。専門家相談は必要に応じた任意のescalation。

## OP-003 屋号

- **何を決めるのか:** 「月の返事」を屋号として使うか、別屋号を使うか、屋号を使わないか。
- **なぜ必要なのか:** provider申込、特商法表記、請求・問い合わせ表示で名称を一貫させるため。
- **選択肢:** 月の返事を屋号として使う / 別屋号を使用 / 屋号なし。
- **推奨案:** サービス名と契約・表示上の名称の関係を利用者が誤認しない形にする。商標クリアランスがあるとは扱わない。
- **今すぐ決める必要があるか:** provider申込情報と公開文面を確定する前に必要。
- **証拠・確認先:** 実際の届出・契約情報、名称利用方針、別途実施するJ-PlatPat検索記録。現時点で商標検索済みとは記録しない。

## OP-005 住所公開方法

- **何を決めるのか:** 特商法表記等で事業者所在地をどの方法で表示するか。
- **なぜ必要なのか:** 通信販売の事業者情報を正確かつ適法に表示するため。
- **選択肢:** 実住所を表示 / 最新の公式案内と採用する表示方法の証拠に基づく別の方法を採用 / 運営形態を見直してから決定。
- **推奨案:** 有料公開前に実在する情報と採用方法を確定し、provider契約情報と整合させる。省略やバーチャルオフィスが常に許されるとは結論しない。
- **今すぐ決める必要があるか:** 現行Stripe Candidate reviewのblockerではない。将来のactual Provider/site review、final URLの審査用ページおよび公開前には、最新の公式一次情報とselected Provider evidenceに基づく実情報・表示方法の確定が必須。
- **証拠・確認先:** 最新の消費者庁公式情報、provider要件、実住所、採用する表示方法および住所利用契約。専門家相談は任意。

## OP-006 電話番号公開方法

- **何を決めるのか:** 特商法表記等で電話番号をどの方法で表示するか。
- **なぜ必要なのか:** 事業者への連絡手段と法定表示を実態に合わせるため。
- **選択肢:** 事業用電話番号を表示 / 最新の公式案内と採用する表示方法の証拠に基づく別の方法を採用 / 運営体制を整えてから決定。
- **推奨案:** 私用番号を無計画に公開せず、実際に受電・折返し可能な運用と表示を一致させる。電話番号の省略が常に許されるとは結論しない。
- **今すぐ決める必要があるか:** 現行Stripe Candidate reviewのblockerではない。将来のactual Provider/site review、final URLの審査用ページおよび公開前には、最新の公式一次情報とselected Provider evidenceに基づく実情報・表示方法の確定が必須。
- **証拠・確認先:** 最新の消費者庁公式情報、provider要件、実番号、採用する表示方法および電話サービス契約。専門家相談は任意。

## OP-007 問い合わせメール

- **何を決めるのか:** 利用者・provider・法務窓口として使う実在のメールアドレス。
- **なぜ必要なのか:** 決済、返金、結果通知、個人情報請求等の連絡を確実に受けるため。
- **選択肢:** 独自ドメインメール / provider-hosted business mailbox / その他の運営者が管理する事業用アドレス。
- **推奨案:** 私用メールと分離し、運営者が継続管理し、利用可能なら二要素認証を有効化し、公開前に送受信試験を行う。
- **今すぐ決める必要があるか:** 現行Candidate taskではProvider contactを行わない。将来のactual Provider submission/contactまたは公開前には実在する連絡先が必要で、exact actionへのHuman authorizationも必要。historical draftには入力しない。
- **証拠・確認先:** ドメイン・mailbox契約、管理権限、二要素認証設定、送受信試験記録。

## OP-008 問い合わせフォーム

- **何を決めるのか:** 問い合わせ受付をフォームのみ、メールのみ、または両方にするか。
- **なぜ必要なのか:** 問い合わせの取りこぼしを防ぎ、必要最小限の情報で適切な対応経路へ振り分けるため。
- **選択肢:** フォームのみ / メールのみ / 両方。
- **推奨案:** 初期運用負荷と障害時の代替経路を踏まえてHumanが決める。採用する経路は、決済問題、重複請求、生成失敗、誤メール、結果URL、プライバシー・削除請求を受け付けられることを事前に試験する。
- **今すぐ決める必要があるか:** provider審査用ページと公開前には必要。フォーム実装はTask 18Cの範囲外。
- **証拠・確認先:** 実在URL、入力項目、通知先、権限、障害時手順、各問い合わせ種別の受信試験。

## OP-009 問い合わせ返信目安

- **何を決めるのか:** 利用者へ表示する通常の初回返信目安。
- **なぜ必要なのか:** 実現可能なサポート水準を事前に示し、返金・不具合・privacy請求の滞留を管理するため。
- **選択肢:** 2営業日 / 3営業日 / 5営業日。
- **推奨案:** 実際の運営可能日とバックアップ体制を確認してHumanが選ぶ。自動では選定しない。
- **今すぐ決める必要があるか:** 問い合わせ窓口の公開前に必要。
- **証拠・確認先:** 運営カレンダー、担当可能時間、テスト運用の実績、緊急対応を提供しない旨の表示。

## OP-020 Analytics有無

- **何を決めるのか:** 初期MVPでアクセス解析を使うか、使う場合はどのprovider・項目・目的に限定するか。
- **なぜ必要なのか:** PrivacyとCookie表示を実際のデータフローに一致させ、不要な追跡を避けるため。
- **選択肢:** 初期MVPでは使用しない / privacy重視の最小構成 / 一般的なanalyticsを事前レビュー後に利用。
- **推奨案:** 明確な計測要件と同意・拒否設計が整うまで初期MVPでは追加しない方向。ただしHumanの未決定事項である。
- **今すぐ決める必要があるか:** 現行Stripe Candidate reviewでは未決定のまま。将来のactual Provider/site review、final legal URLsおよびPaid Launch/publication前には、実装有無とPrivacy・Cookie記載を一致させる必要がある。
- **証拠・確認先:** 実装コード、network通信、provider契約・設定、取得項目、保持期間、拒否方法。

## OP-021 Cookie方針

- **何を決めるのか:** 必須Cookieと任意Cookieの範囲、説明、同意・拒否方法。
- **なぜ必要なのか:** 実際のサイト動作とPrivacy・Cookie説明を一致させるため。
- **選択肢:** 必須Cookieのみ / analytics等を含み目的別に選択可能 / 別Cookie Policyを作成。
- **推奨案:** 初期MVPは必須用途へ最小化し、任意計測を導入する場合だけ追加の同意・拒否設計を行う方向。法的要件は最終構成に基づき確認する。
- **今すぐ決める必要があるか:** 公開前に必要。Task 18Cで実装・確定しない。
- **証拠・確認先:** 実ブラウザのCookie・storage・network確認、provider仕様、最新の公式情報、必要に応じた任意の専門家相談。

## OP-026 結果URL有効期限

- **何を決めるのか:** 結果ページへアクセスできる期間と、期限後の扱い。
- **なぜ必要なのか:** 利用者の再閲覧利便性と、漏えい・長期保持リスクを調整するため。
- **選択肢:** 7日 / 30日 / 90日 / Humanが根拠を記録した別期間。
- **推奨案:** 無期限にはせず、初期候補として30日を比較検討する。保存期間、再発行手順、利用者表示との整合を確認するまで最終決定しない。
- **今すぐ決める必要があるか:** 初期readiness文書作成だけでは完了不要だが、production-use applicationでdelivery条件を確定する時点、結果ページ実装、Privacy・特商法のfinal publicationおよびPaid Launch前には必要。
- **証拠・確認先:** 利用者ニーズ、security設計、database削除・token失効試験、最新の公式情報および実際の保存・削除運用。専門家相談は任意。

## OP-027 結果URL失効・再発行

- **何を決めるのか:** URL紛失、誤メール、漏えい疑い時の失効・再発行・本人確認手順。
- **なぜ必要なのか:** 第三者閲覧を防ぎながら、正当な購入者の再アクセスを支援するため。
- **選択肢:** 再発行なし / email所有確認後に再発行 / 個別サポート審査後に再発行。
- **推奨案:** email所有確認後に旧tokenを失効し、新tokenを発行する案を基準に検討する。回数制限、監査記録、例外は実装・privacy確認後に決める。
- **今すぐ決める必要があるか:** 初期readiness文書作成だけでは完了不要だが、production-use applicationのfinal customer-support/delivery条件、結果ページとサポート運用の実装およびPaid Launch前に必要。
- **証拠・確認先:** token失効・再発行試験、本人確認フロー、監査ログ、Privacy・削除手順。

## OP-029 マーケティングメール

- **何を決めるのか:** 初期MVPでマーケティングメールを行うか。
- **なぜ必要なのか:** 結果通知と広告配信の目的・同意・解除記録を混同しないため。
- **選択肢:** 初期MVPでは行わない / 任意の分離されたオプトインで行う。
- **推奨案:** Humanが明示的に有効化しない限り、初期MVPではマーケティングメールを行わない。
- **今すぐ決める必要があるか:** 初期MVPの公開設計前に必要。これは推奨であり、完了済み判断ではない。
- **証拠・確認先:** Human決定、同意画面、同意・解除記録、Email provider条件、最新の公式情報。

## OP-034 `needs_review`の取扱い

- **何を決めるのか:** 初期MVP後に`needs_review`を扱う場合の別運用。初期MVPの扱いはすでに決定済み。
- **なぜ必要なのか:** 安全性が未確認の相談を通常鑑定・決済へ誤って流さないため。
- **選択肢:** 初期MVPでは決済不可・通常鑑定なし / 将来、別タスクでHuman review等を設計して承認。
- **推奨案:** 承認済み方針どおり、初期MVPでは決済へ進めず、通常の恋愛鑑定書やメッセージ案を生成しない。将来の扱いは別途承認する。
- **今すぐ決める必要があるか:** 初期MVPの方向は内部決定済み。将来運用は今決めず、別タスクと証拠が必要。
- **証拠・確認先:** Human承認記録、server-side safety gate試験、返金・監査設計。Task 18Cでは実装しない。

## OP-035 鑑定書の共有

- **何を決めるのか:** 鑑定書の保存、引用、SNS共有、再配布をどこまで許可するか。
- **なぜ必要なのか:** 利用者の私的利用と、全文転載・転売・商用再配布の境界を明確にするため。
- **選択肢:** 私的利用のみ / 限定的な抜粋共有 / 全文共有可。
- **推奨案:** 個人的・私的利用を基本とし、小さな抜粋共有は将来検討する。転売と全文の商用再配布は禁止する方向。
- **今すぐ決める必要があるか:** 初期readiness文書作成だけでは完了不要だが、production-use applicationに使用するfinal利用規約URL、Paid Launch/publication前にはHuman判断と、最新の公式一次情報・実際の利用条件・最終公開文言の確認が必要。最終決定とは扱わない。
- **証拠・確認先:** Human決定、利用規約案、AI生成物の権利・利用許諾に関するcurrent-source review。専門家相談は任意。
