# 月の返事 PRODUCT_SPEC.md v0.4

## 0. このドキュメントの位置づけ

このドキュメントは、AIを活用した恋愛メッセージ分析・判断支援デジタルレポート「月の返事」のプロダクト親仕様書である。ユーザー向け定義は「恋のメッセージ鑑定ノート」とする。

Status note: 以下の旧Phase順序は成立時点の履歴として保持する。現在の実行順序、完了定義、次タスクおよびHuman gateは `docs/ROADMAP.md` が優先し、旧Phase番号自体は実装・問い合わせ・デプロイを承認しない。

現時点では本番Webアプリ・ネイティブアプリの実装は行わない。
まずは以下の順番で検証し、Go条件を満たした場合のみ実装フェーズに進む。

1. Phase 0：AI鑑定品質ラボ
2. Phase 1：半自動¥980有料検証
3. Phase 2：自動Web MVP
4. Phase 3：相手別ノート＋低額サブスク
5. Phase 4：ネイティブアプリ化
6. Phase 5：月額4,000円級プレミアム

最重要ルール：

- 需要検証なしにコードを書かない
- 7日以上ラボにこもらない
- 自己採点だけで進めない
- Day5から集客を始める
- 単発¥980が売れるまでサブスクを本命にしない
- Webで検証する。ネイティブアプリは後
- コイン/ポイント制は採用しない
- 不安を煽って課金させない
- 危険相談は通常鑑定にしない
- AI利用は隠さない

## 1. プロダクト概要

### サービス名

月の返事

### 一言定義

月の返事は、返信待ち・追いメッセージ・曖昧な関係で不安になる夜に、利用者が入力した関係状況やメッセージをAIが整理・分析し、「このメッセージを送っていいか」「今は待つべきか」「この関係に時間を使っていいのか」の判断材料を、恋のメッセージ鑑定ノートとして返すサービスである。

### 表向きの訴求

送る前に読む、恋のメッセージ鑑定ノート。

### 深層価値

返事を待つ夜に、不安で暴走する前に、入力された状況と次の一手を整理する場所。

Human-approved emotional objective:

> 恋愛の不安に対して単に答えを出すだけではなく、利用者の気持ちを少し軽くし、ひとりで考え続ける状態から抜け、次の行動を自分で選べる状態をつくる。

判断の正確さだけでなく、不安を増幅しない、急がせない、責めない、相手の本心を断定しない、迷いを整理する、再判断の時期と条件を示す、利用者自身の決定余地を残すことをUX品質とする。

## 2. なぜこの企画にするのか

便利ツールではなく、すでに課金心理がある深い感情領域に寄せる。

狙う感情：

- 彼の気持ちが分からない
- 返信が来なくて不安
- 追いメッセージしたい
- でも重いと思われたくない
- 曖昧な関係を続けていいのか分からない
- 友達には何度も相談できない
- 電話占いは高い
- でも今夜どうすればいいか知りたい
- ChatGPTよりも「自分の恋を読まれた感じ」がほしい
- 不安を受け止めてほしいが、暴走は止めてほしい

狙う市場心理：

恋愛相談・占いコンテンツに支払う既存の課金心理 × メッセージ送信前の迷い × 夜の衝動

これは市場心理に関する観察であり、月の返事を占いサービスと定義するものではない。

## 6. コア体験

チャットではなく、1入力 → 1鑑定書。

初期MVPの有料成果物は、同じ将来の構造化結果を基にしつつ、表示目的の異なる二層に分ける。

- `月の返事 鑑定ノート`: 理由、文面案、3日間の行動、注意点を縦に深く読むWeb版
- `保存用鑑定書`: 結論、再判断の目安、条件、文面案等を後で短時間に見返す保存版

保存用鑑定書はWeb版のスクリーンショットでも、Web全文を小さく押し込んだものでもない。A4一枚/複数枚、PDF/画像、download方法等は未決定であり、M1-I4で承認され得るのはfixture previewまでとする。

チャット型にしない理由：

- ChatGPTと比較されやすい
- 無限会話でAPIコスト・依存リスクが上がる
- 個別レポートの特別感が出にくい
- 単発課金の価値が弱く見える
- 鑑定書/手紙として保存価値が出せる
- 結果を画像・HTML・PDF的に見せやすい

基本フロー：

1. 夜に不安になる
2. アプリ/LPを開く
3. 今の状況をそのまま書く
4. 送ろうとしているメッセージを貼る
5. 関係性や知りたいことを軽く選ぶ
6. 入力内容の整理・分析が始まる
7. 「今夜の返事」という鑑定書が届く
8. 送る/待つ/軽く送る/送らないの判定が出る
9. 送るなら文面候補が出る
10. 保存して後から見返せる
11. 将来的には相手別ノートに蓄積される

## 7. 入力UX：鑑定依頼シート

ユーザーに細かいフォームを埋めさせない。
不安な夜に、事務手続きをさせない。

採用する入力UXは、自由入力中心の「鑑定依頼シート」。

初期有料Web MVPの入力はテキストのみとする。情報設計は少なくとも `現在の状況`、`実際のやり取り`、`送ろうとしている文面` の3領域を扱う。1ページか複数ステップかはM1-I2開始前のHuman gateとして未決定のまま残す。

LINE等の会話は必要部分のコピー貼付を積極的に案内する。入力欄付近では、名前を「相手」「自分」「Aさん」等へ置換し、実名、電話番号、住所、勤務先等を削除するよう案内する。画像/file inputは初期MVPに追加しない。

### ユーザーに見せる入力

#### 1. 大きな自由入力欄

表示文言例：

> 今の状況を、そのまま書いてください。
> まとまっていなくても大丈夫です。返事が来ないこと、相手との関係、送ろうとしている言葉、不安な気持ちをそのまま置いてください。

#### 2. 送ろうとしているメッセージ欄

表示文言例：

> 送ろうとしている文面があれば貼ってください。

#### 3. 関係性チップ

- 曖昧な関係
- 片思い
- 交際中
- 復縁したい
- マッチングアプリ
- 連絡待ち
- その他

#### 4. 知りたいことチップ

- 送っていいか
- 待つべきか
- 相手の気持ち
- この関係を続けていいか
- 文面が重くないか
- 今後どう動くべきか

#### 5. 個人情報入力禁止の注意

表示文言例：

> 実名、住所、電話番号、勤務先、SNS IDなど、個人を特定できる情報は入力しないでください。相手の名前も仮名やイニシャルで入力してください。

### 裏側でAIが構造化する項目

- 相手との関係
- 最後の連絡状況
- 返信待ち期間
- 追いメッセージ回数
- 相手の温度感
- ユーザーの感情
- 送ろうとしている文面の重さ
- 判定に必要な材料
- 危険フラグ
- 不足情報
- 推奨判定

## 8. 鑑定書構成

鑑定書は以下の構成を基本にする。

1. 今夜の結論
2. 今の関係の整理
3. 相手側にあり得る受け止め方
4. あなたが不安になっている核心
5. この文面がどう伝わる可能性があるか
6. 今夜の推奨アクション
   - 送っていい
   - 軽く送るならあり
   - 今夜は待つ
   - 今日は送らない方がいい
7. 送る場合の文面案
8. 3日間の行動プラン
9. この分析の限界と注意点

重要なのは、ただ優しいだけではなく、判定を下すこと。

判定だけで終了してはならない。`送っていい`、`軽く送るならあり`、`今夜は待つ`、`今日は送らない方がいい`の全正常ラベルで、今回の判断、判断理由、再判断の目安、方針を変える条件、待っている間の行動、連絡がない場合の次の選択肢、後で送る場合の文面案、断定できないことを含める。根拠なく `明日18時` 等の精密な時刻を断定しない。

ChatGPTとの差別化：

- ChatGPT：両論併記しがち
- 月の返事：今夜は送る/待つ/軽く送る/送らないを出す

## 9. AI人格・文体

AI感は前面に出しすぎない。
ただし、AI利用は隠さない。

人格：

優しく状況を読み解きながら、衝動的・危険な行動は止める分析者。

特徴：

- 不安を否定しない
- 不安を煽らない
- 相手の気持ちは断言しない
- 複数の可能性として読む
- 追いメッセージ・長文・問い詰めは冷静に止める
- 月・夜・手紙のブランドらしい余韻を出す
- でも現実的
- 最後は具体的な文面や行動に落とす

NG文体：

> 彼はあなたを愛しています。今すぐ連絡しましょう。

目指す文体：

> 入力内容から見ると、相手の気持ちが完全に離れたと決めつける材料は不足しています。ただ、今夜の不安のまま長文を送ると、確認したい気持ちよりも重さが先に伝わる可能性があります。送るなら、気持ちを確かめる文ではなく、軽く温度を見る一言に留める方が安全です。返信の有無は保証できません。

## 10. AI構成

MVP段階ではローカルLLMは使わない。

採用方針：

OpenAI API + 独自プロンプト + 鑑定書テンプレ + 判定ロジック + 安全フィルター

ローカルLLMを使わない理由：

- 初期検証が遅れる
- 日本語の情緒表現が弱くなりやすい
- GPU/運用コストが重い
- 今はモデル研究ではなく課金検証が先
- 差別化はモデルではなく、体験・テンプレ・記憶・世界観で作るべき

AI処理フロー：

1. 入力
2. 安全判定
3. 相談内容の構造化
4. 事実・推論・不足情報の分離
5. 判定エンジン
6. 鑑定書生成
7. 出力チェック
8. 保存用要約生成
9. 表示/納品

判定と文章生成は分ける。

- 判定パート：低temperature、構造化出力、安定性重視
- 鑑定書生成パート：情緒・世界観・言葉の質を重視

## 11. 月・夜のブランドレイヤー

「月の返事」という名前と視覚世界を支えるブランド演出として、月、夜、手紙、ノート、月明かりのモチーフを使用できる。

注意：

- 月齢、月相、星座その他の天体情報を分析入力、判定根拠または未来予測に使用しない
- 月を擬人化した表現は詩的な締めに限り、隠れた事実や未来を教える存在として扱わない
- タロット、占星術、生年月日、数秘術、霊感その他の占術・超自然的手法を使用しない
- 実質的な分析根拠は利用者が入力した情報だけとする

## 13. コイン/ポイント制は採用しない

初期MVPでは、コイン制・ポイント制は採用しない。

理由：

- 悪質占いサイトに類似して見える
- 価格が分かりにくくなる
- 資金決済法上の前払式支払手段の論点が出る可能性がある
- 決済審査で不利になる可能性がある
- 初期検証のデータが汚れる
- 不安を利用した継続消費に見えやすい
- 「あと少しで分かる」型の引き延ばしに見えやすい

将来的に前払い型を導入する場合も「コイン」ではなく、「鑑定チケット」として検討する。
ただし、法務・決済審査後に限る。

## 16. 安全設計

このアプリは、医療・カウンセリング・診断ではない。

位置づけ：

AI恋愛メッセージ分析・状況整理・判断支援・エンターテインメントおよび情報提供。

避ける表現：

- うつが治る
- 精神疾患を改善
- カウンセリング
- 診断
- 必ず復縁できます
- 彼はあなたを愛しています
- 課金しないと彼が離れます
- 相手を操作できます
- 監視できます

危険入力は通常鑑定にしない。

検知対象：

- 自傷

## 18. 禁止表現リスト

### 絶対禁止

- 彼はあなたを愛しています
- 必ず復縁できます
- 今すぐ送れば戻ってきます
- 課金しないと彼が離れます
- 今見ないと手遅れです
- この鑑定で悪い未来を避けられます
- 続きの鑑定を受けないと流れが切れます
- 相手を操作できます
- 監視すれば分かります
- 診断します
- 治療します
- カウンセリングします

### 回避訴求型コピー禁止

定義：

鑑定を受ければ恋愛上の重大な不利益を回避できるかのように見せる表現。

適用範囲：

- LP
- 広告
- X投稿
- アプリ内コピー
- Push通知
- 鑑定文
- メール
- サブスク訴求

禁止例：

- 鑑定しないと彼の気持ちは離れます
- 今すぐ見ないと手遅れになります
- このままだと復縁の可能性が消えます
- 課金すれば悪い流れを止められます
- 続きの鑑定を受けないと未来が悪くなります

代替表現：

- 送る前に、言葉の温度を見直す
- 不安なまま送る前に、今夜の流れを読む
- この関係にどう向き合うかを整理する
- 送る/待つ/距離を見る、次の一手を考える
- 返事を待つ夜に、心を少し整える

## 19. 返金ポリシー

基本方針：

デジタル鑑定書という商品の性質上、納品後の返金は原則不可。

ただし、以下の場合は将来の全額返金候補として扱い、provider選定後の運用/法務仕様で確定する。

- 例外的に決済成功後のSafety再判定で通常鑑定を提供できない場合
- サービス側都合で納品できない場合
- 重複決済
- 明らかな提供不能
- その他、運営側が返金すべきと判断した場合

内部draft方向（publication-readyではない）：

> デジタル鑑定書という商品の性質上、納品後の返金は原則としてお受けできません。ただし、重複決済または決済後の提供不能が確認された場合は、全額返金の対象候補となります。具体的な返金方法・条件・時期は決済事業者選定後に確定します。

Safetyは決済前に実施し、`normal_allowed`のみ将来の購入フローへ進める。`needs_review`、`rejected`、年齢/同意不備、矛盾入力、unknown/errorは購入不可とする。

将来、決済成功後にSafety再判定、AI出力Safety、継続失敗またはシステム障害で提供不能となる例外に備え、下流Milestoneでは次の状態列を設計する。

```text
payment_succeeded
  -> fulfillment_blocked or fulfillment_failed
  -> refund_required
  -> operator_attention_required
  -> refunded
```

提供不能時は通常レポートを出さず、復旧可能なら再試行し、復旧不能なら全額返金候補として扱う。二重返金防止、理由/状態記録、operator通知、ユーザーへの結果または返金状況案内を要件とする。ただし、自動返金、providerの返金API、手数料返還、期限、反映日数、具体的管理画面操作はprovider選定後まで断定しない。

## 22. Go/No-Go基準

### Go

- LPセッション300以上
- 有料購入10件以上
- 返金要求1件以下
- 「保存したい」「また使いたい」発言3件以上
- 14日以内リピート、または明確なリピート意向2件以上
- 外部評価で刺さる文言が確認できる
- 危険相談で安全分岐できる

### 延長

- 購入3〜9件
- 反応はあるがCVRが弱い
- LPや訴求に改善余地が明確

7日だけ延長。

### No-Go

- セッション300以上で購入0〜2件
- 外部評価が悪い
- ChatGPTで十分と言われる
- 保存したい/また使いたいが出ない
- 危険ケースの処理が不安定

### チャネルNo-Go

LPに人を集められない場合は、商品ではなく集客の問題として別管理する。
