# Guidance Quality R1 — 回答成立と行動判断の正本

日付：2026-09-07。状態：Humanが今回承認したProduct方向性の正本化。実装案・編集上の目標例・新評価ケースの実モデル品質は未検証。LOCAL ONLY。

## 1. 適用範囲と優先関係

月の返事は、相手の本心・未来・関係の正解を確定するサービスではない。「相手の気持ちはまだ分からないが、今どう考え、どう動けばよいかは少し整理できた」という方向性を返す。980円の価値は、相談に合った方向性、その理由、役立つ次の一歩に置く。文章量・項目数・重厚な分析では代替しない。

本書は [PRODUCT_SPEC](../PRODUCT_SPEC.md) の回答品質に関する後継正本。旧§6・§8の固定3日間、全ラベルへの待機中行動・将来文面等の一律要求、および旧R2-C計画の「短い・材料が少ないだけで商品候補から外す」方向は、本書と衝突する範囲で今後のProduct判断に適用しない。旧実験・受入記録・snapshotは保存する。既存の事実分離、条件付きtradeoff、文字数で価値を測らない思想は継承する。

[AI_PROMPT_GUARDRAILS](../ai/AI_PROMPT_GUARDRAILS.md) の全正常ラベルへの固定項目要求や「待つ方が安全」という文体例も、今後の品質設計では本書の条件付き方針に従う。同文書の危険行動・断定・捏造禁止は維持する。価格、Payment順序、Auth、Safety、通知、R1防御、Provider/model、DB・Production設定を変更しない。これは稼働中prompt/schema/classifierの上書き承認ではない。

## 2. 回答の成立

相談者が決めたいことに応じて方向性を返し、入力に沿う理由と使える次の一歩を示す。不明点は、確度・回答範囲・詳しさを調整して扱う。一部の問いが未成立でも、答えられる問いまで原則失わせない。

- 普通の1〜3文、相手の気持ち・普段の返信間隔・細部の日時が不明というだけでは全体停止しない。
- 文面だけ整えたい相談は、自然な編集と意味の説明で成立し得る。関係全体の判定や送信可否の決め直しを必須にしない。既に自然な原文には「そのままでよい」と返せる。
- 送らないことが主提案なら、文面案を作らない回答で成立し得る。送る場合でも目的と次の一歩が明確なら、将来は文面を一律必須にしない方向。現行send/reply schemaの必須性は互換課題として残る。
- 複数の文面案・複数解釈・固定3日間・細かい予定・独立した慰めsection・注意書き一覧は品質の必要条件ではない。
- 関係の結論や本心を答えられなくても、自然なお礼、質問への返信、誘い、予定確認、今夜の気持ち整理には答えられる。

実質的に空、対象外、危険行動の支援は別扱い。対象文面の意味を保つ編集なのに原文がない等、答えを成立させるために本当に必要な情報だけを、一つの具体的な質問で確認する。普通の不確実性を解消するための質問票や、新しい連続確認Gateは作らない。既存の一回確認予算や支払い順序を変更する承認ではない。

例：「お礼は送ってよいか」と「この文面はどう伝わるか」が混在し原文だけない場合、お礼の方向性は成立し、文面の印象だけは未確認とできる。実装時の部分成立の表示・課金前表現は別の互換設計が必要。

## 3. 行動判断

送る不利益と送らない不利益の両方を、相談に関係する範囲で比較する。毎回比較表や両論併記sectionを要求しない。

| 場面 | 判断に使う事実 | 区別するもの |
| --- | --- | --- |
| 会った後のお礼 | 会った事実・お礼の目的・連絡境界 | お礼と「私を好き？」という好意確認 |
| 相手からの連絡 | 発話者・質問／挨拶・その後の応答 | 自然な返信と自分の未返信連絡への追加送信 |
| 初めての誘い | 初回か・断りや境界・断れる余地 | 誘うことと受諾／好意の予測 |
| 予定確認 | 仮約束・未確定事項・現実の期限 | 段取り確認と返信／気持ちの催促 |
| 返信待ち | 未返信数・経過・新しい用件 | 通常待機と連投を止める制止 |
| 境界 | 明示文面・許された例外とその用途 | 距離の尊重と相談全体のSafety対象外化 |

自然なお礼や返信、無理のない初回の誘い、必要な予定確認は前向きに後押しする。好意が確定するまで行動できないとはしない。明確な拒否・連絡境界や連投を無視した接触を、勇気づけの名目で勧めない。通常の業務上の感謝は、business-only境界の違反と一律に見なさない。

「一通送って、その後は返事を待つ」は主行動が送信。待機語の数で分類しない。Safety対応、境界尊重、未返信連投の制止、通常の待つ、相談者が望む気持ち整理を別分類する。

送信率の増加、送る／待つ50対50、リピート購入、相談者が望む結論への同調を最適化しない。複数方向が妥当なら許容し、推奨理由と選択余地を示す。

## 4. 壊してはいけない品質境界

以下は文体改善と同列に扱わない。

- 入力にない出来事・理由を事実として追加しない。「忙しいから未返信」は、本人からそう聞いた入力がなければ事実ではない。
- 引用、候補文面の意味・由来を偽らない。「土曜は無理」を「土曜なら空いている」に変えない。好意確認を削除した別案を「同じ意味の添削」と称さない。
- 本心・未来・返信を断定しない。
- 危険行動や境界侵害を支援しない。
- 「送る」と「今は一切送らない」等の矛盾した現在行動をそのまま提供しない。将来条件による見直しは時間と条件を分ける。
- 技術障害、欠落したProvider出力、検証できない候補を一般論で埋めて納品扱いにしない。

成立した回答の軽い硬さ、短さ、実害のない繰り返し、不要sectionの欠落は改善対象であり、それだけで相談を回答不能としない。同じfinding codeでも、何が壊れたか、どの文面か、意味と行動への影響を評価する。severity名やcodeによる一括許容・拒否へ置換しない。

## 5. 相談状態・候補状態・提供状態

| 概念 | 例 | Product上の扱い |
| --- | --- | --- |
| 相談には答えられる | お礼を送るか迷っている | 情報の範囲内で方向性を返す |
| 一項目だけ未成立 | 対象文面がない | その項目を限定し、必要なら一問 |
| 候補の修復が必要 | 入力にない都合を文面に足した | 候補を修復・再検証。相談自体が回答不能とは言わない |
| 候補が成立し改善余地のみ | 自然なお礼と理由はあるが語尾が少し硬い | 改善対象。全体の喪失を正当化しない |
| 提供できる検証済み候補がない | 改善版が壊れ、以前の候補の完全性も未確認 | 技術／品質失敗として区別。架空回答で納品しない |

F008のRecovery engineは今回実装しない。「以前の候補」は、同じ相談・同じ入力・同じ決定／Safety／文面所有権に対する完全なPlan＋Reportの組で、守るべき境界を満たすと確認できた場合だけ将来の採用検討対象となる。途中のstage片、別入力の候補、未評価候補を正常と推定しない。初回が全検査正常なら現行は再評価しないため、「常に正常候補を捨てる」とは説明しない。
