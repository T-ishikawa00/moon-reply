# Customer Identity Threat Model V1

- Status: `design_only_pending_human_chatgpt_review`
Scope: Supabase Auth Customer identity, anonymous-to-authenticated binding, account/history, result recovery, and the existing RC-1/RC-2 Payment/Delivery chain

## 1. Security invariants

1. Only a server-verified `auth.users.id` is Customer identity.
2. Browser input never selects or supplies the authoritative CustomerUserId.
3. One preparation can be bound once; another Customer cannot overwrite it.
4. Email equality never creates, transfers, or merges ownership.
5. Auth never proves Payment. Existing verified-Payment authority remains unchanged.
6. A service-role operation must carry an explicit ownership predicate because RLS does not constrain service role.
7. Capabilities are narrow bearer authorities, stored hash-only server-side, and never become account identity.
8. Uncertainty denies binding, checkout, private result disclosure, linking, and deletion completion.
9. Customer cookie Auth uses only the publishable key; privileged repository/admin authority uses only the secret key. The trust domains never inherit one another's authority.
10. V1 has no browser Supabase Auth client, no `createBrowserClient`, and no localStorage Auth token.

## 2. Mandatory cases

| # | Threat | Prevention | Detection | Recovery | Fail-closed behavior |
| --- | --- | --- | --- | --- | --- |
| 1 | Stolen preparation capability | Capability cannot bind by itself. Require a purchase-ready preparation, short-lived one-use Auth continuation, same-origin initiation, verified Supabase session, row lock, and unique binding. Keep raw capabilities out of URLs/logs where the existing flow permits. | Rate-limit events, continuation conflicts, repeated preparation lookups, and different-Customer bind attempts; log only opaque event IDs. | Revoke pending continuations and preparation capability where supported; regenerate the anonymous preparation before Payment. A completed binding is never transferred automatically. | If capability, continuation, state, session, or preparation status is missing/ambiguous, create no binding or Checkout. Residual risk remains before first binding if all anonymous authority is stolen; it cannot expose already-bound paid history. |
| 2 | Stolen result URL | New account access uses Auth ownership. Keep result tokens hash-only, purpose-bound, revocable, out of logs/referrers/previews, and disclose them narrowly. Prefer Auth account links for new notification mail. | Detect unusual token failures/access patterns without recording raw token, email, or result content. | Revoke and rotate the result credential after verified Customer recovery; preserve canonical delivery. | Invalid/revoked/expired tokens disclose nothing. A valid legacy bearer token still carries residual bearer risk; this architecture does not falsely claim otherwise. |
| 3 | Stolen browser session | Traditional server-only Auth; Secure, HttpOnly, SameSite=Lax, host-only cookies; request-scoped server refresh; short access JWT; no browser client/localStorage; fresh `getUser()` and detached-state checks for high-impact actions. Desired inactivity/absolute limits remain a Pro-plan or reviewed-equivalent activation gate. | Session/user mismatch, impossible usage patterns, refresh reuse/failure, and explicit Customer report. | Revoke current/all sessions, clear cookies, require the original supported Google/OTP identity, and rotate affected result credentials. | Detached/revoked/expired session denies checkout, binding, history, result disclosure, linking, and deletion actions. |
| 4 | OAuth callback manipulation | PKCE, high-entropy validated state/continuation, exact redirect allowlist, one-use callback, code exchange server-side, and server-selected relative return path. | State/PKCE mismatch, callback replay, unexpected origin/return target, and duplicate consumption metrics. | Revoke continuation, clear incomplete Auth cookies, restart from purchase-ready state. | No binding or session is accepted when any callback field or flow binding is invalid. |
| 5 | CSRF | Non-GET mutations, exact Origin/Host checks, an independent per-continuation `csrf_token_hash`, SameSite cookie defense, and no callback GET state change beyond validated PKCE exchange/continuation. Raw continuation and CSRF tokens are distinct and never persisted. | Origin/token/continuation failures and abnormal repeated mutation attempts. | Revoke the continuation/session and ask the Customer to retry from the purchase-ready state. | No bind, checkout, logout-all, link, or delete mutation occurs without every applicable CSRF/continuation check. |
| 6 | Account takeover | Google/Email OTP only; no reusable Customer password; provider protections; non-enumerating OTP request; rate limits/CAPTCHA; reauthentication for high-impact actions; no provider-token storage. | Auth rate-limit/CAPTCHA events, new-session notification where later approved, repeated sensitive-operation failures, Customer report. | Revoke all sessions, freeze new checkout, reverify identity through a reviewed support flow, rotate result credentials. | Suspected takeover blocks private reads and mutations; support cannot transfer ownership on email assertion alone. |
| 7 | Email OTP brute force | Supabase verification limits plus application per-IP/per-destination/per-continuation limits, short OTP TTL, bounded retries, CAPTCHA escalation, and constant/non-enumerating responses. | 429/verification-failure counters by privacy-safe keyed identifiers; alert on distributed patterns. | Revoke the OTP/continuation, cool down, issue a fresh OTP after threshold, offer Google login if already linked. | Exhaustion or uncertainty consumes/revokes the flow; no session or binding is created. |
| 8 | Duplicate account creation | Test both orderings but apply the actual asymmetric policy: Email-first may gain a later same-email OAuth identity; Google-first Email OTP/signup must not be assumed to link or send mail. Keep Email responses non-enumerating and ownership keyed only by Auth UUID. | Detect duplicate/conflict signals without exposing whether an email exists or its provider. Never treat a shared email as merge authority. | Google-first Customers use Google again in V1. Freeze ownership transfer and use a reviewed, reauthenticated support workflow for true duplicates. | Obfuscated OTP success is never treated as delivery or a linked identity. Separate users remain isolated; no history crosses accounts. |
| 9 | Unsafe account merging | No merge by raw email, Google email, Stripe email, Customer name, or support assertion. Manual linking is disabled in V1; there is no promised Google-first -> Email OTP fallback. | Link-conflict events, ownership on both candidate users, provider-identity mismatch, and verifier rejection of symmetric-linking claims. | Preserve both identities and bindings; a future supported linking/transfer path requires new acceptance, reauthentication, idempotency, and conflict proof. | Any conflict or unsupported ordering cancels linking without changing either account. |
| 10 | One Customer claims another Customer's purchase | Unique preparation binding, row lock, same-preparation composite FK, verified session, exact continuation, one-way binding, repository ownership checks. | Different-Customer bind conflict, repeated status/result access denials, concurrency test failures. | Revoke leaked continuation/capability; preserve the original binding; support investigates without disclosing identity. | Existing binding always wins. A different Customer receives a generic conflict and no purchase metadata. |
| 11 | Result-history IDOR | `/account` and result routes derive CustomerUserId from the verified server session and join Customer -> binding -> Purchase -> Delivery in one constrained query. Use opaque public identifiers and no client-selected ownership key. | Cross-Customer synthetic tests, denied-access metrics, repository query-shape verifier. | Revoke session/result credential, patch the query, review access logs and affected deliveries under incident procedure. | Not-owned and not-found return the same privacy-safe response; no partial row or existence signal. |
| 12 | Deleted account attempts recovery | Detachment state blocks reads, sessions are globally revoked, result credentials are revoked, and Auth user is deleted after DB detachment. Retained Payment evidence has no active CustomerUserId. | Access attempts against detached ownership reference, Admin deletion retry state, stale JWT attempts. | Complete pending Auth deletion; Human/legal handling can inspect retained evidence without restoring account ownership. A new account is a new identity. | Deleted identity cannot reclaim history by reusing email, Google login, status capability, or an old session. Any exceptional restoration requires a separate accepted process. |
| 13 | Service-role bypass, credential mixing, or missing ownership check | Separate trust domains: Customer `createServerClient` accepts only publishable key/cookies; repository/admin accepts only secret key and no Customer session. Keep secret server-only, use minimal ACL, typed ownership-constrained repositories/RPCs, negative tests, and code review. | Static verifier for publishable/secret mixing, cross-Customer integration tests, query audit, secret scanning, and anomalous broad result counts. | Disable affected route, rotate leaked secret if applicable, patch client construction/predicate/RPC, and assess exposure. | Any Customer Auth client using secret authority, repository using publishable authority, or repository/RPC lacking an ownership constraint is non-releasable even when RLS is enabled. |
| 14 | Google or Supabase provider outage | Keep anonymous browsing/drafting available, separate Auth from Payment authority, and use bounded retries only before mutation. The clean cutover never reopens legacy mailbox verification when Auth is selected, even under Auth emergency stop. | Provider health/error rates, callback/refresh failures, circuit-breaker state. | Resume from purchase-ready preparation after provider recovery; do not recreate consultation or Purchase Intent. Offer Email OTP only if Supabase Auth itself remains healthy. Any pre-existing legacy recovery need requires its separately accepted transition. | No new binding, legacy verification, or Checkout when identity cannot be verified. Existing verified Payment continues fulfillment independently. |
| 15 | Email provider outage | Separate Supabase Auth SMTP from application result mail, durable notification outbox/idempotency, safe provider errors, bounded retry, and alternate Google login where already possible. | Auth send failures, Step E outbox delivery state, provider health, retry exhaustion; no recipient/content logging. | Retry the same idempotent notification/OTP flow within authority, switch login method where safe, preserve account/history access and canonical result. | Never report an email as sent without provider evidence; never create a session from an unsent/unverified OTP; email failure never reverses verified Payment or duplicates fulfillment. |

## 3. Residual risks requiring explicit acceptance

- The retained legacy `/result/[token]` route is still a bearer capability. Auth-based account access reduces new-path dependence but does not retroactively remove theft risk.
- An entirely stolen anonymous preparation authority before first binding can still be abused to attempt a claim. V1 limits and detects this; it cannot prove a real-world person before authentication. Once any Customer binds, paid history is not transferable.
- Email OTP security inherits mailbox security. It is not phishing-resistant MFA.
- Google and Supabase availability becomes a gate for new paid-flow entry. Payment fulfillment remains independently recoverable after verified Payment.
- Server-mediated service-role access concentrates responsibility in repository/RPC ownership checks. Missing checks are release-blocking defects, not risks delegated to RLS.
- Exact retention periods and incident-notification obligations require Human legal review before Private Release.
- Real Auth activation additionally requires a read-only zero-active-legacy-customer inventory. If a real legacy Purchase/Payment/Delivery still needs Customer recovery, clean cutover is blocked until a separate recovery transition is accepted.

## 4. Verification minimum

The implementation task must add deterministic tests for all 15 cases, including concurrency for bind conflict, cross-Customer fixtures, callback replay, CSRF rejection, OTP threshold behavior through fakes, detached-account denial, service-role missing-predicate detection, provider-outage recovery, `/purchase/auth/:path*` refresh coverage, Auth-OFF legacy compatibility, and Auth-ON legacy-write denial. No real Google, Supabase Auth email, Resend email, Stripe Payment, or production Customer data is needed for this proof.
